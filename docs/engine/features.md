## 0. Engine version: read this first
- **FalkorDB 6.0.0 (Sep 29 2026) is the first release on a new engine written in Rust.** It replaces the C engine used by every 4.x release. Same Redis module (`graph`), same `GRAPH.*` commands, same Cypher, same clients. Replication now sends only *effects* (format v3), so 4.x and 6.0 can't be mixed in one replica set, and `EFFECTS_THRESHOLD` is ignored. Full-text and vector indexes now run on RediSearch 8.6.1 (up from 2.6.23). Docker tags `latest` and `6.0.0` point at the Rust engine; `v4.x.y` and `edge-c` stay on C; there are no Alpine images for 6.0. Source: https://github.com/FalkorDB/FalkorDB/releases (6.0.0 notes). Since then: 6.0.1 (Oct 1, dependency refresh) and 6.0.2 (Oct 8). 6.0.2 fixes a wrong-dimension vector dropping an entity from every index on its label, clamps vector KNN `k`, validates vector index OPTIONS, fixes UDF edge cases, fixes GRAPH.CONSTRAINT/GRAPH.MEMORY parsing, and runs Docker as a non-root user.
- **The 6.0 notes say directly: "6.0 has the same procedures as 4.20.7".** A* (`algo.AStar`), CCH (`algo.CCH`) and Leiden/Louvain "have not shipped in any release" on the new engine and "are being ported". However, **v4.22.0 (C engine, Sep 30) does ship A*, Yen's k-shortest paths and the CCH index**. So the docs pages for A* and CCH describe the 4.22 line, not 6.0.
- **This contradicts the team's spike.** The spike (research/v3_00 line 4) ran on `falkordb/falkordb:latest` and the engine reported **module 42201 = 4.22.1**, not 6.0. Possible explanations: an old cached `latest` image, or the tag being repointed. **UNVERIFIED which.** Pulling `latest` today could switch engines mid-build. **Pin the exact tag you spiked on, re-run the spikes on it, and write the tag in the README.**
- FalkorDB is pushing 6.0 hard: X launch post on Sep 29 (https://x.com/falkordb/status/2104931495823430120), blog "Announcing FalkorDB 6.0" (Sep 29), "Rewriting FalkorDB in Rust" (Aug 3).

## 2. Loved by the sponsor but unused: ranked by fit with the headline
1. **Constraints (UNIQUE + MANDATORY): fits headline items 1 and 4.** Make the database itself enforce the citation gate and the lease invariants. Suggested constraints:
   - `MANDATORY` on `Hypothesis.status` and `Event.id`
   - `UNIQUE` on `Event.id`, `Task.id`, `Hypothesis.id` (each needs an exact-match index first)
   - `MANDATORY` on the `REFUTED_BY`/`SUPPORTED_BY` relationship property `evidence_id`

   Then a refute edge without a cited ID **fails at write time**, and duplicate task IDs can't happen. This gives "deterministic gate, not the LLM" an engine-level backstop. (FalkorDB constraints only check existence and uniqueness, not cross-node references, so the "cited ID exists" check stays in the single write query's `MATCH`.) Low risk; it's one command per constraint.
2. **GRAPH.RO_QUERY with a timeout, plus showing the Cypher: fits Q\* and the "show how it got there" brief.** Run every agent read and Q\* through `RO_QUERY` with a timeout, and display the executed Cypher and path in the UI. This exact habit was singled out in FalkorDB's own Sep 30 recap. Optional: use the `version` argument so a resuming agent detects that the graph changed under it (**UNVERIFIED** in practice; spike it first).
3. **Temporal types (`localdatetime`, `duration`): fits headline items 1, 3 and 4.** Store `refuted_at`, `lease_expires`, `claimed_at` as `localdatetime` and lease length as `duration`. Then lease expiry is `WHERE t.lease_expires < localdatetime()` inside the atomic claim query, and you can show a "time-to-refute" stat. This matches the "close outdated facts instead of appending" message (blog Oct 16). Caveat: only `local*` types are documented (no timezone), so use one server clock, which PLAN §7 already does.
4. **UDFs (JavaScript) plus FLEX similarity: fits headline item 3 (repeated failed steps).** Load one small UDF library such as `sheldon.sameAction(a, b)` (normalise and compare action signatures), or use FLEX `jaccard`/`levenshtein` to flag a "semantically equal action to a prior failure" **inside Cypher**. The repeated-steps metric then becomes a query, not Python. FalkorDB pushed programmable UDF traversal (May 14), and 6.0.2 fixed UDF edge cases (Oct 8). Keep it to one or two functions; check FLEX availability on the pinned image (**UNVERIFIED** that FLEX is preloaded).
5. **Graph algorithms on the investigation graph (WCC, betweenness): fits Q\* and the demo.** Two cheap options:
   - `algo.WCC` on `Hypothesis`/`Event` nodes to show "disconnected lines of inquiry"
   - `algo.betweenness` restricted to `CAUSED_BY|RESULTED_IN|SUPPORTED_BY` to rank the "pivot evidence", meaning the event whose refutation would invalidate the most tasks

   Use them as a supporting panel, not the core. Use config-map syntax (spike note: whole-graph algos take no positional args). `algo.SSpaths`/`algo.BFS` from a refuted action node is an algorithmic cross-check of Q\*'s blast radius.
6. **MCP server (official, v1.3.0 has schema discovery): fits headline item 4.** Point one agent (e.g. Claude Desktop/Cursor) at the official `@falkordb/mcpserver` **in read-only mode** as the "inspector" agent that resumes the investigation. This shows FalkorDB-native tooling with zero custom MCP code. Still optional; keep it at the bottom of the cut order.
7. **Browser 2.7 (3D view, Chat panel): fits the demo.** Already used. Showing the Oct 15 3D view or the Chat panel on the investigation graph is a free nod to their newest release.
8. **GRAPH.MEMORY / db.meta.stats: fits the per-investigation graph story.** One line in the demo ("investigation graph = X MB, N nodes") supports the "one graph per investigation" choice with their own command. Trivial.
9. **GRAPH.COPY: weak fit right now.** check.md (claim #5) shows a rival already uses it, and the PLAN marks it stretch. If time is left: copy the investigation graph before running S0 vs S3 eval runs so every run starts from the same state. That uses it honestly without novelty claims.
10. **Edge vector / full-text indexes on relationships.** Possible on `HANDED_OFF` notes or `REFUTED_BY` reasons, but adds little. Skip.

## 3. Doesn't fit, or risky for a ~36h build
- **A\*/CCH, point/`distance()`, MaxFlow, MSF:** no geography or flows in incident memory. A\*/CCH also aren't in 6.0. Mentioning them would look like feature-stuffing.
- **Global PageRank as "HippoRAG PPR":** there is no personalized PageRank (check.md #9). Don't claim it.
- **Bolt:** experimental, "not meant to be used in production".
- **Replication/cluster/HA:** async replicas can lag, so a stale read could break lease semantics. 6.0 also changed replication. Out of scope.
- **Switching engine mid-build (4.22 ↔ 6.0):** the biggest real risk. Pin the image tag.
- **FalkorDBLite:** bundles server 4.18.3 (older than your spike). Fine for CI, but don't demo on it without re-running the spikes.
- **Building on GraphRAG-SDK:** document ingestion isn't the headline, and it would blur "original work" (stuff.md l.385). Citing its abstention/provenance idea is fine.
- **MULTI/EXEC for coordination:** it serializes across all graphs (PLAN §4). Keep the single-query lease.
- **Vector-with-filter claims:** don't say the docs "forbid" it (check.md #7).
